# VimEngine Stage 8 — Transactional Host Integration

Stage 8 replaces Calcite's per-edit Vim handoff with a revision-aware transaction boundary. One logical Vim command now carries its exact sequential edit script, a normalized non-overlapping batch for the original snapshot, before/after state, repeat metadata, origin, and a stable transaction identifier.

## Implemented

### Atomic Vim transactions

`VimExecutionResult` exposes an SPI-only `VimEditTransaction` without changing the ordinary public EditorVim API. The transaction records:

- The base document revision and origin
- Exact sequential UTF-16 edits generated by the engine
- A normalized base-snapshot edit batch
- Vim state before and after execution
- Repeatability and insert-mode completion metadata
- A stable transaction identifier

Compound operations such as Visual Block delete, change, paste, indentation, and replicated insertion are delivered as one host transaction.

### Atomic document pipeline

`EditorDocumentPipeline.applyEdits` applies a non-overlapping edit batch through one document-session call and schedules analysis once after the complete batch is accepted.

`EditorTab.submitVimTransaction` validates the base revision and source text, applies the optimistic UI update once, remaps highlights, build diagnostics, breakpoints, and snippet stops, increments the visible revision once, and recovers from the authoritative backend snapshot if application fails.

### Revision-aware document session

`VimDocumentSession` now applies exact transaction batches rather than reducing every command to one prefix/suffix diff. It reports accepted, rebased, rejected, and desynchronized outcomes.

If the document changes while the session is suspended, one non-overlapping external edit is rebased. Overlapping changes are rejected instead of silently overwriting newer content, and the engine is restored from the authoritative document snapshot.

### External edit reconciliation

`VimEngine.reconcileExternalText` transforms cursor, marks, jumps, change positions, and Visual endpoints through safe external edits.

- Non-overlapping edits preserve Normal or Visual state.
- Overlapping Visual edits cancel the affected Visual interaction.
- External edits during Insert, Replace, active change, or block insertion cancel unsafe transient state.
- Conflicts publish the stable `VIM_EXTERNAL_CONFLICT` message code.

The Calcite document synchronizer distinguishes an acknowledged local Vim transaction from a formatter, LSP, reload, or other external snapshot, avoiding destructive full synchronization for locally accepted edits.

### Host capability and result boundary

Calcite-facing host requests now include an invocation identifier and originating context:

- Document URL
- Editor session identifier
- Selection
- Document revision

`VimHostCapabilities`, `VimHostResponse`, and `VimHostFailure` distinguish accepted, completed, unsupported, cancelled, stale-context, and failed actions. Host failures are converted into structured Vim status messages.

Document-scoped requests are routed back to the originating tab and rejected when its document revision is stale, rather than being applied to whichever tab later became active.

### TextKit visual geometry

EditorVim now accepts an optional SPI geometry provider. Calcite supplies a TextKit-backed implementation for:

- Proportional-font visual columns
- Soft-wrapped vertical movement
- Tab and glyph layout positions
- Grapheme-safe point-to-offset conversion
- Visual Block projection

Every geometry method may return `nil`; EditorVim then uses its deterministic terminal-style display-column implementation.

### Calcite integration decomposition

The Vim-specific integration boundary is split into focused components:

- `CalciteVimDocumentSynchronizer`
- `CalciteVimGeometryProvider`
- `CalciteVimCursorPresenter`
- `CalciteVimSelectionPresenter`
- `CalciteVimViewportProvider`
- `CalciteVimHostRouter`
- `CalciteVimInputAdapter`
- `CalciteVimMessagePresenter`

The AppKit coordinator remains the lifecycle owner, but revision tracking, geometry, cursor presentation, selection projection, viewport calculation, input translation, message translation, and host routing no longer live as independent policies inside it.

## Environment limitation

The validation environment is Linux. It cannot run Xcode, AppKit, TextKit rendering, native macOS accessibility, or installed Korean/Japanese/Chinese input methods. The macOS sources were parser-validated, while the complete portable package and test suite were compiled and executed.
